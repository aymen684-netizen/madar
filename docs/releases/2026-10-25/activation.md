2. بعد اعتماد التفعيل، تحديث حقلي `production_settings.build_command` و
   `production_settings.deploy_command` في إعداد Worker Builds فقط إلى:

   ```json
   {
     "production_settings": {
       "build_command": "node scripts/fetch-reviewed-release.mjs",
       "deploy_command": "npm run deploy"
     }
   }
   ```

3. إعادة قراءة الإعدادات للتأكد، ثم دمج الطلب الجامع. يتيح هذا الترتيب وجود المستورد في commit

4. تنشئ مراجعة `main` حزمة واحدة وتختبرها. بعد نجاح الفحوص، تنشر Pages الأصول نفسها، ثم ينشر
   `distribute` أرشيف GitHub Release وبصمته. الصيغة هي
   `madar-<sourceSha>-<runId>-<attempt>`؛ حزم PR غير مؤهلة للنشر.
5. ينتظر Cloudflare أحدث مراجعة مطابقة لـ`WORKERS_CI_COMMIT_SHA` على `main`، وينزّل الأرشيف
   العام ويفحص SHA-256 والإيصال والمدخلات وسجل المراجعة. ينتظر حتى 18 دقيقة، ويوقف البناء
   عند الفشل أو انتهاء المهلة. لا يعيد تجهيز الأصول أو تجميع Worker.
6. ينفذ `npm run deploy` تحققًا مستقلًا قبل الرفع. إذا تجاوزت المراجعة مهلة Cloudflare، يعاد
   تشغيل بناء commit نفسه بعد نجاحها؛ لا يُستبدل أمر المستورد بأمر بناء المصدر لتجاوز البوابة.

## أدلة النجاح المطلوبة

- نجاح جميع وظائف المراجعة على commit النهائي لـ`main`، ثم `pages` و`distribute`؛ ليست نتيجة
  PR بديلًا عن مراجعة commit الدمج النهائي.
- وجود الأرشيف والبصمة تحت tag التشغيل الصحيح، ومطابقة `release.json.sourceSha` و
  `review.json.sourceSha` ونتيجة Actions لذلك commit.
- نجاح بناء Cloudflare وظهور إصدار Worker جديد فعال بنسبة 100% مرتبط بهذا البناء.
- مقارنة بايتات HTML وملفات JavaScript والعامل والبيانات المنشورة بعينات من الحزمة المراجعة،
  والتحقق من ترويسات الحماية وإعادة التحقق `ETag`/`304` ومسارات API المحمية. تستخدم أصول
  Cloudflare `public, max-age=0, must-revalidate`؛ ترويسات Pages تحت إدارة GitHub وتُسجل كما هي.
- تشغيل فحص النسخة المنشورة واختبار الإقلاع والواجهة العربية والإنجليزية وتنزيل Word.

تختبر فحوص PR ضغط الحزمة وفكها والتحقق من كل ملفاتها، ورفض المسارات الهاربة والروابط والبصمة
الخاطئة والمراجعة الفاشلة. تبقى دورة نشر الأرشيف العام وتنزيله من Cloudflare بحاجة إلى تحقق
بعد التفعيل؛ لا يمكن إثباتها من تشغيل PR الذي يمنع النشر.

### فحص ما بعد النشر

ينفذ المسار `.github/workflows/post-deploy.yml` بعد نجاح تشغيل `Review application` من `push` على `main` فقط. يتحقق أولًا من نجاح فحص Cloudflare `Workers Builds: madar` المربوط بمعرّف commit نفسه؛ **نجاح مراجعة GitHub وحده لا يثبت اكتمال نشر Cloudflare**.

بعدها ينزل `scripts/fetch-reviewed-release.mjs` حزمة الإصدار الأصلية ويعيد التحقق من SHA-256 وإيصال مراجعة GitHub؛ ثم يقارن HTML وJavaScript وWorker وبيانات اللغة الإنجليزية وWord على استضافتي Cloudflare وGitHub Pages بالبايتات المراجعة ويتحقق من `ETag/304`. أخيرًا يشغل `scripts/check-cloudflare.mjs` واختبار المتصفح `MADAR_BROWSER_SMOKE=1`. تحفظ الأدلة ضمن مرفقات تشغيل `Verify reviewed production deployment`.

لا تدخل هذه الوظيفة ضمن الفحوص العشرة التي تمنع دمج Pull Requests؛ فهي تعتمد على نشر يحدث بعد الدمج. تُراجع نتائجها في GitHub Actions بعد **كل** نشر، ويستدعي فشلها التحقيق، وليس إعادة النشر دون فهم السبب.

### الرجوع عند حدوث مشكلة

1. سجّل إصدار Cloudflare الحالي وcommit المصدر وسجل مراجعة GitHub، وحدد إذا كان خللًا في Worker أو في بيانات/أصول GitHub Pages أيضًا.
2. إذا كانت المشكلة حرجة في Worker، **يمكن** إعادة تفعيل نسخة مراجعة سابقة ناجحة من قائمة Deployments (مثل `beae1018-9315-4431-94d8-d419e499d313` إذا كانت لا تزال متوفرة وصالحة). افحص ارتباطها بالمصدر ونتائج مراجعتها قبل توزيع 100% من الزيارات؛ لا تعتمد رقمًا تاريخيًا ثابتًا دون فحص الحالة الفعلية.
3. تحقّق من ترويسات الأمان ومسارات API ومن Word والمتصفح بعد الرجوع؛ قارن GitHub Pages بصورة منفصلة فقد يظل يعرض نسخة أحدث.
4. إذا احتجت رجوع المصدر/Pages، افتح طلب دمج يعكس التغيير عبر حماية `main` والفحوص العشرة، ولا تستخدم Force Push أو حذف السجل. تجنب إعادة الأوامر الإنتاجية القديمة إلا إذا كان الرجوع يستدعي بالفعل نسخة مصدر قديمة لا تملك آلية الحزمة المراجعة؛ عندها يلزم إجراء مستقل وموافقة مدونة.
5. إذا كان النشر التلقائي قد يعيد نشر نسخة معيبة أثناء الاستجابة للحادث، أوقفه مؤقتًا بإجراء واضح موثق، ثم أعد تشغيله بعد التصحيح وإعادة الاختبار.

**حدود الإثبات:** وجود إصدار سابق محفوظ لا يضمن التوافق الدائم بين Worker وGitHub Pages أو مصادر البيانات؛ يجب اختبار الاستضافتين بعد أي رجوع. هذا القسم يوثّق إعدادات 26 أكتوبر، وليس ضمانًا لصحة أي نشر لاحق.
